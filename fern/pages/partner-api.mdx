---
title: LettBestilt Partner API
subtitle: Create and manage restaurants from your own systems
---

The LettBestilt Partner API, under `https://www.lettbestilt.no/api/v1/partner`, lets you create sandboxes, read a restaurant's setup, rotate and revoke its keys, manage its webhooks and domains, import its menu from a PDF or photo, invite its owner and ask LettBestilt for go-live approval, set up its settings, opening hours, delivery zones and menu ([Set up a restaurant through the API](/partner-setup-api)), and manage your own partner account: brand, logos, sender domain, profile and news to your restaurants ([Your own partner account](/partner-setup-api#your-own-partner-account)), without opening LettBestilt Partner (the partner portal). Everything it does can also be done in the portal. The same setup is available to AI assistants through [LettBestilt MCP](/mcp).

<Note>
Test partner keys (`lbp_test_…`) see and create only sandboxes. Live partner keys (`lbp_live_…`) reach real restaurants and can be created in the partner portal once LettBestilt Partner is open; until then, real restaurants are created in the partner portal, and inviting the owner and asking for go-live approval are done there too. The endpoints for real restaurants are described below so you can build against them.
</Note>

## Two keys

| | Partner key | Restaurant key |
|---|---|---|
| Looks like | `lbp_test_…` | `lbs_test_…` or `lbs_live_…` |
| Belongs to | Your partner account | One restaurant |
| Created in | Partner portal → **Settings → Partner key** | Partner portal → the restaurant's API section, or returned when you create a restaurant through the API |
| Works against | `/api/v1/partner` only | The rest of `/api/v1` (menu, orders, reservations …), and `/api/v1/partner` together with the partner key |

The partner key alone can only see the surface and create new restaurants. Anything that touches an existing restaurant also needs that restaurant's own key. A leaked partner key can therefore not read details about, change or delete a restaurant.

| Call | Partner key alone | Partner key + restaurant key |
|---|---|---|
| `GET /partner/restaurants` (list) | ✓ | |
| `POST /partner/restaurants` (create) | ✓ | |
| `GET /partner/restaurants/{slug}` (details) | | ✓ |
| `DELETE /partner/restaurants/{slug}` | | ✓ |
| `POST …/keys/{keyId}/rotate`, `DELETE …/keys/{keyId}` | | ✓ |
| `GET`, `POST …/webhooks`, `DELETE …/webhooks/{webhookId}` | | ✓ |
| `GET`, `POST …/domains`, `DELETE`, `PATCH …/domains/{domainId}`, `POST …/domains/{domainId}/verify` | | ✓ |
| `POST …/menu-imports`, `GET …/menu-imports/{importId}`, `POST …/menu-imports/{importId}/commit` | | ✓ |
| `/me`, `/brand`, `/brand/logo`, `/brand/logo-light`, `/brand/sender-domain`, `/profile`, `/news` ([your own partner account](/partner-setup-api#your-own-partner-account)) | ✓ | |
| `…/settings`, `…/hours`, `…/delivery-zones`, `…/menus`, `…/categories`, `…/products`, `…/addon-groups` ([setup](/partner-setup-api)) | | ✓ |
| `POST`, `DELETE …/owner-invite` (real restaurants) | | ✓ |
| `POST`, `DELETE …/go-live-review` (real restaurants) | | ✓ |

Send them like this:

```http
Authorization: Bearer lbp_test_...
X-LettBestilt-Restaurant-Key: lbs_test_...
```

Rules for the pair:

- Both keys must be in the same environment. A test partner key with a live restaurant key fails with `401 UNAUTHORIZED`.
- The restaurant key must have full access (scope `*`). A key limited to some scopes gives `403 INSUFFICIENT_SCOPE`. The key you get when you create a restaurant has full access.
- The `slug` in the path must match the restaurant key. A slug that does not exist, belongs to another partner or does not match the key always gives the same `404 RESTAURANT_NOT_FOUND`, so the API never tells you who owns a slug.
- Older restaurant keys without an environment in the prefix (`lbs_<random>`) are not accepted. Rotate them in the partner portal first.
- The partner key is rejected on every other `/api/v1` endpoint with `401`. Use the restaurant key there, as before.

## Server to server only

Call the partner API from your back end. A request with an `Origin` header is rejected with `403 FORBIDDEN`, and preflight requests get no `Access-Control-Allow-*` headers, so a browser can never use it. Never put a partner key in browser code, a mobile app or a repository.

## Create a restaurant

`POST /partner/restaurants` with a test partner key creates a **sandbox**: a restaurant that is never live, has no ordering page on `{slug}.lettbestilt.no`, and accepts test orders through `/api/v1`. A partner can have up to 20 sandboxes.

The `Idempotency-Key` header is **required**. Use a new key, for example a UUID, for every restaurant you want to create, and reuse it only to retry that request.

<CodeBlocks>
```bash title="cURL"
curl -X POST "https://www.lettbestilt.no/api/v1/partner/restaurants" \
  -H "Authorization: Bearer $LETTBESTILT_PARTNER_KEY" \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{"name":"Pizza Roma (test)","slug":"pizzaroma-test","email":"dev@byraet.no"}'
```

```typescript title="TypeScript"
const API = "https://www.lettbestilt.no/api/v1/partner";

const res = await fetch(`${API}/restaurants`, {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.LETTBESTILT_PARTNER_KEY}`,
    "Idempotency-Key": crypto.randomUUID(),
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    name: "Pizza Roma (test)",
    slug: "pizzaroma-test",
    email: "dev@byraet.no",
  }),
});

if (res.status === 201) {
  const { data, restaurantKey } = await res.json();
  // Shown once. Store it in your secret store right away.
  await saveSecret(`lettbestilt/${data.slug}`, restaurantKey.key);
}
```
</CodeBlocks>

The `201` response contains the new restaurant key in plain text, **once**, in `restaurantKey.key`. Store it before you do anything else: every call about this restaurant needs it, and LettBestilt cannot show it again.

`orgNumber` is optional. When you send it, it must be a valid Norwegian organisation number: 9 digits with a correct check digit (mod 11). Spaces are fine. An invalid number gives `422 VALIDATION_FAILED` with an issue in `error.details.issues` whose `path` is `"orgNumber"`, and nothing is created.

### Real restaurants

With a live partner key, `POST /partner/restaurants` creates a real restaurant. Before anything is created, LettBestilt checks, in this order:

| Check | Error |
|---|---|
| LettBestilt has approved your partner account | `403 PARTNER_NOT_APPROVED` |
| Your partner agreement and data processing agreement are signed, and still current | `403 PARTNER_AGREEMENT_REQUIRED` |
| Your support email, support phone and invoice email are filled in | `403 PARTNER_PROFILE_INCOMPLETE`, with the missing fields in `error.details.missing` (`supportEmail`, `supportPhone`, `invoiceEmail`) |

The restaurants and their customers see your support email and phone, in the customer agreement and on the restaurant's legal page, so they can reach you. LettBestilt sends your invoice to the invoice email. Set them under **Innstillinger → Merkevare** and **Innstillinger → Profil** in the partner portal, or with [`PATCH /partner/brand` and `PATCH /partner/profile`](/partner-setup-api#contact-and-invoice-details).

**New terms mean a new signature.** If LettBestilt changes something in your signed partner agreement, such as the price or your company's name or organisation number, the signature no longer counts. The team member who signs gets an email, and signs again under **Kom i gang** in the partner portal. Until then, the restaurants you have keep working, but a new real restaurant gives `403 PARTNER_AGREEMENT_REQUIRED`.

The body also needs `customerPrice` (`startupFeeOere`, `monthlyFeeOere`, optionally `bindingMonths` and `freeMonths`): what the restaurant pays you, in øre and whole kroner. It goes into the customer agreement the owner signs and cannot be changed after that. Without it: `422 VALIDATION_FAILED` with `path: "customerPrice"`.

Sandboxes (test partner key) need none of this.

### Retries and replays

The `Idempotency-Key` is remembered per partner for 30 days.

| You send | You get |
|---|---|
| Same key, same body | `200` with the same restaurant, `replayed: true`, `restaurantKey: null`, a `message`, and the header `Idempotent-Replayed: true` |
| Same key, different body or environment | `409 IDEMPOTENCY_CONFLICT` |
| Same key, but the restaurant has since been deleted or moved | `409 IDEMPOTENCY_CONFLICT` |

A replay never returns the restaurant key again. If the first response was lost (a timeout, for example) and you never stored the key, create a new key for the restaurant in the partner portal.

A slug that is already in use gives `409 SLUG_TAKEN`. That does not count towards the limit on creations.

## Read, list and delete

- `GET /partner/restaurants` lists your restaurants with slug, name, environment, whether it is live or archived, and when it was created. It is paginated: pass `nextCursor` back as `cursor` until it is `null`. `limit` is 1–100 (default 25).
- `GET /partner/restaurants/{slug}` returns setup status, SagaPay status (`payment`), owner status (`owner`) and go-live status (`goLive`) (these three are `null` for sandboxes), `showPoweredBy` (whether the website shows "Drevet av LettBestilt"), verified domains, webhooks without secrets (with `pausedReason`, see [Webhooks](#webhooks)), and the restaurant's keys: name, last four characters, environment, scopes and expiry.
- `DELETE /partner/restaurants/{slug}`:
  - **A sandbox is deleted for good**, together with its keys. A second `DELETE` with the same key therefore gives `401`. Confirm with the list that the slug is gone. A sandbox with accounting records that must be kept cannot be deleted (`409 RETENTION`).
  - **A real restaurant is never deleted.** It is archived: turned off and closed in `/api/v1`, while orders and accounting records are kept. Its webhooks are paused. You can still read it, revoke its keys and delete its webhooks, but not rotate keys or add webhooks (`409 RESTAURANT_ARCHIVED`). **Only LettBestilt can restore an archived restaurant.**

```typescript title="TypeScript"
const res = await fetch(`${API}/restaurants/pizzaroma-test`, {
  method: "DELETE",
  headers: {
    Authorization: `Bearer ${process.env.LETTBESTILT_PARTNER_KEY}`,
    "X-LettBestilt-Restaurant-Key": restaurantKey,
  },
});
const { data } = await res.json(); // { result: "deleted", slug: "pizzaroma-test" }
```

## Keys and webhooks

- **Rotate** a restaurant key with `POST …/keys/{keyId}/rotate`. The new key gets the same scopes and the same expiry date, and the old one keeps working for `graceHours` (default 24). See [Rotating keys without downtime](/rotating-keys).
- **Revoke** with `DELETE …/keys/{keyId}`, now (`graceHours: 0`, the default) or after up to 24 hours. You cannot revoke the key you are calling with immediately (`409 KEY_IN_USE`); rotate it instead.
- **Webhooks**: `GET …/webhooks` lists them, `POST …/webhooks` creates one (the signing secret is in the response, once), `DELETE …/webhooks/{webhookId}` removes one. A restaurant can have up to 10. Pausing, resending and test events are in the partner portal; see [Webhooks](/webhooks).
- **Webhooks on a real restaurant carry customer data**, so a new webhook is only active when its host is a domain of the restaurant that a person verified, or your website. Otherwise it is created paused (`paused: true` in the response), with `pausedReason` saying why. The partner API cannot turn a webhook on, and LettBestilt MCP's `set_webhook_active` gives `403 WEBHOOK_HOST_NOT_TRUSTED`: a person turns it on on the restaurant's **Webhooks** tab in the partner portal. The lists show `pausedReason` for such a webhook (otherwise `null`). Sandboxes are not affected.

Key ids are in `apiKeys` in `GET /partner/restaurants/{slug}`.

## Domains

A verified domain lets the restaurant's site call `/api/v1` from the browser and use the domain for `successUrl` and `cancelUrl`. See [Authentication](/authentication#trusted-browser-origin).

- `POST …/domains` with `{ "domain": "www.pizzaroma.no" }` adds a domain. The response has the TXT record in `verification` (`name` is `_lettbestilt-verify.www.pizzaroma.no`, plus a `value`). Add it at the DNS provider.
- `POST …/domains/{domainId}/verify` looks up the record and verifies the domain. It is safe to repeat: an already verified domain gives `200`. If the record is not found yet you get `422 DOMAIN_NOT_VERIFIED`; DNS changes can take a while.
- `GET …/domains` lists all domains, including those waiting for verification.
- `PATCH …/domains/{domainId}` with `{ "primary": true }` makes a verified domain the one LettBestilt's tracking links in emails and on receipts go to.
- `DELETE …/domains/{domainId}` removes a domain. A domain LettBestilt manages gives `409 DOMAIN_MANAGED`.

A restaurant can have up to 10 domains (`409 DOMAIN_LIMIT`). A domain registered for another restaurant gives `409 DOMAIN_TAKEN`, unless it has stayed unverified there for more than 72 hours, or it is unverified on a sandbox and you add it to a real restaurant; then you take it over and get `200` with a new TXT value. Domains work for sandboxes too.

## Menu import

Upload the restaurant's menu as a PDF or a photo, check the proposal, and import it as a new menu:

1. `POST …/menu-imports` as `multipart/form-data` with the file in the field `file`: a PDF (up to 4 MB and 20 pages) or a JPEG, PNG or WebP image (up to 4 MB). HEIC is not supported. The response (`201`) is a draft with `proposal`: categories, products, sizes, prices in øre and suggested allergens, each with a `confidence` and the `reasons` a line is uncertain. Sending the same file as an open draft returns that draft (`200`). The call can take a couple of minutes.
2. Check the proposal. A language model reads the menu. For a PDF with a text layer, every price and name is checked against the text. An image or a scanned PDF cannot be checked that way: `proposal.source.checkedAgainstText` is `false`, and the proposal has the warning `CHECK_AGAINST_MENU`. Check every price against the menu before you import.
3. `POST …/menu-imports/{importId}/commit` creates a **new menu that is turned off**. Send `proposal` with your corrections, or leave it out to use the stored one. No existing menu is changed. Customers see the new menu only once the restaurant turns it on and makes it the default menu (or gives it a schedule).

Drafts are deleted after 7 days. A second commit, also after a lost response, gives `409 MENU_IMPORT_CLOSED` with `details.menuId`, so a retry finds the menu. The file itself is never stored. Allergens are suggestions; the restaurant must confirm them.

## Inviting the owner

`POST …/owner-invite` with `{ "name": "…", "email": "…" }` emails the restaurant's owner an invitation. The owner creates their own login, signs the customer agreement and the data processing agreement, sets up online payment with SagaPay and sets the restaurant live. You cannot do those steps for the owner.

`payment.state` tells you who acts next: `NOT_STARTED` (the owner has not applied for online payment), `WAITING_FOR_OWNER` (the application is with the owner: registration with BankID, signing or more information), `IN_PROGRESS` (SagaPay is setting it up), `ACTIVE` and `FAILED` (the application stopped; the owner can start again under Betaling in the dashboard). Subscribe to the [`PAYMENT_SETUP_UPDATED`](/api-reference/webhooks/payment-setup-updated) webhook to be told when it changes, for example to remind the owner while it is `WAITING_FOR_OWNER`. The restaurant can go live with cash payment while online payment is not ready.

- For real restaurants without an owner only, so it needs a live key. A sandbox gives `409 SANDBOX_NOT_SUPPORTED`, and a restaurant with an owner gives `409 OWNER_EXISTS`.
- The invitation expires after 7 days. Calling again resends it, replaces the open invitation (also to a different email) and gives 7 new days. `Idempotency-Key` is not used.
- The email cannot belong to a partner user or a member of the restaurant (`422 OWNER_EMAIL_NOT_ALLOWED`).
- `502 INVITE_SEND_FAILED` means the invitation is saved but the email did not go out. Send the same call again shortly.
- `DELETE …/owner-invite` revokes the open invitation. `owner.status` and `owner.inviteId` in `GET /partner/restaurants/{slug}` show where it stands.

## Go-live approval

A real restaurant needs LettBestilt's approval before it goes live for the first time. The owner signs the agreements. LettBestilt approves the restaurant before the owner sets it live.

1. When the steps under **Get started** (*Kom i gang*) are done, `goLive.readyToRequest` in `GET /partner/restaurants/{slug}` is `true`. Before that, a request gives `422 GO_LIVE_NOT_READY` with the missing steps in `details.missing`. `goLive.missingSteps` lists them as keys, and `goLive.missingStepDetails` gives each one a Norwegian name and says what is missing and who does it:

   | Key | Name | What is missing |
   |---|---|---|
   | `agreement` | Kundeavtale | The owner signs the customer agreement in Kom i gang |
   | `dpa` | Databehandleravtale | The owner signs the data processing agreement in Kom i gang |
   | `invoice` | Fakturaopplysninger | Organisation number, legal name and invoice method (EHF, or e-mail with an invoice address) |
   | `hours` | Åpningstider | At least one open day, confirmed in Kom i gang |
   | `fulfillment` | Henting og levering | Pickup or delivery on (delivery needs an active zone), confirmed in Kom i gang |
   | `prep-times` | Tilberedningstid | The preparation times, confirmed in Kom i gang |
   | `payment` | Betaling | The owner confirms the payment methods in Kom i gang, also when only payment on pickup is on |

   Until you send the request, `goLive.currentChecks` has LettBestilt's checklist as it is now, with the texts (`level`, `title`, `detail` per check), so you can fix errors first. The Brønnøysund Register Centre and the website are only checked when you send the request (`probed: false`). `lastChecks` is the checklist from the latest request.
2. `POST …/go-live-review` sends the request. LettBestilt's checklist runs first (menu, opening hours, payment, agreements, company details, website, domain, API key, owner, allergens and more). Errors give `422 GO_LIVE_CHECKS_FAILED` with every check in `details.checks`, and nothing is sent. Warnings do not stop the request.
3. LettBestilt reviews the restaurant. `goLive.state` becomes `approved` or `rejected`, with LettBestilt's comment in `goLive.comment` when it is rejected.
4. The owner sets the restaurant live. An approval never does that by itself, and it is valid for 30 days.

`DELETE …/go-live-review` withdraws a request that is still waiting. Real restaurants only: a sandbox gives `409 SANDBOX_NOT_SUPPORTED`.

## Rate limits

| What | Limit |
|---|---|
| All partner endpoints | 120 calls per minute per partner key |
| Create a restaurant | 10 per hour per partner key, and 20 per hour per partner. Replays do not count |
| Delete or archive a restaurant | 10 per hour per partner key |
| Rotate or revoke keys, create or delete webhooks, add, remove or change domains, owner invitations, commit menu imports, and every write in [Set up a restaurant through the API](/partner-setup-api) and [Your own partner account](/partner-setup-api#your-own-partner-account) | 30 per minute per partner |
| Owner invitations | 5 sent per hour per restaurant and 30 per partner; 20 attempts per hour per restaurant and 60 per partner |
| Verify a domain | 30 per 10 minutes per restaurant |
| Go-live requests | 15 per hour per restaurant and 30 per partner; withdrawing 10 per hour per restaurant |
| Menu imports | 10 uploads per hour per restaurant and 60 per partner, 20 readings with the language model per 24 hours per restaurant; commit 10 per hour per restaurant |

Over the limit you get `429 RATE_LIMITED` with `Retry-After`. The limits for owner invitations, domain verification and go-live requests are shared with the partner portal, and the hourly limit on menu uploads with the restaurant dashboard.

## Responses and errors

- Every response with content wraps it in `data`. Responses are never cached (`Cache-Control: no-store`) and always carry `X-Request-Id`.
- Validation errors are `422 VALIDATION_FAILED` with `error.details.issues`, also for `limit` and `cursor`. Invalid JSON is `400 INVALID_JSON`.
- Calls with a restaurant key appear in that restaurant's API log in the partner portal. Calls with the partner key alone (list and create) do not, because they are not about one restaurant. See [Debugging with request IDs](/debugging).

All codes are listed in [Errors](/errors), and every endpoint in the [API reference](/api-reference).
