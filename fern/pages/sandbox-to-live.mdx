---
title: From sandbox to live
subtitle: Build against a sandbox, then switch one restaurant to real orders
---

A sandbox is a test restaurant that belongs to you, the partner. It answers in `/api/v1` with a test key, takes test orders and simulated online payments, and is kept out of SagaPay, invoicing and accounting. You build the whole site against it, then point the finished site at the real restaurant.

<Steps>

### Create a sandbox

Either in LettBestilt Partner (the partner portal), or with the [LettBestilt Partner API](/partner-api):

```bash
curl -X POST "https://www.lettbestilt.no/api/v1/partner/restaurants" \
  -H "Authorization: Bearer $LETTBESTILT_PARTNER_KEY" \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{"name":"Pizza Roma (test)","slug":"pizzaroma-test","email":"dev@byraet.no"}'
```

Store `restaurantKey.key` from the response. It is a test key (`lbs_test_…`) with full access, and it is shown only once. You can have up to 20 sandboxes.

Emails from a sandbox, such as order confirmations, only go to your own partner addresses, never to the address a test customer types.

### Build the site against the sandbox

Use the test key from your server exactly as you will use the live key later:

```bash title=".env.local"
LETTBESTILT_SLUG=pizzaroma-test
LETTBESTILT_API_KEY=lbs_test_...
```

To place test orders, the sandbox needs products and opening hours, like any restaurant. Orders outside the kitchen's opening hours are rejected.

### Test payments

Create an order with `paymentMethod: "STRIPE"`. In a sandbox, `stripeUrl` points to LettBestilt's test payment page instead of SagaPay:

- **Betal (test)** marks the order `PAID`, sends `ORDER_PAID` to your webhooks as a real payment would, and returns the customer to `successUrl`.
- **Avbryt** (cancel) marks the order `FAILED` and returns the customer to `cancelUrl`. No webhook is sent, as with a real abandoned payment.
- In a sandbox, `successUrl` and `cancelUrl` may also point to `localhost`, `127.0.0.1`, `[::1]` (http or https, any port) or `https` `*.vercel.app`. When you go live, they must be on the restaurant's verified domain.

No money moves. `restaurant.capabilities.payment.online` is `true` in a sandbox when online payment is turned on, so your checkout shows it. See [Payments](/payments#testing-payments-in-a-sandbox).

### Test webhooks

Create a webhook for the sandbox (portal or `POST /partner/restaurants/{slug}/webhooks`) and use **Send test event** (*Send testhendelse*) in the portal to check that your endpoint verifies the signature. Then place a test order and follow the deliveries in the webhook's delivery log. See [Webhooks](/webhooks).

### Check the integration

In the restaurant's API section in the partner portal, **Check integration** (*Sjekk integrasjonen*) shows whether the key has been used, webhooks are delivered, the API log has errors and your return URLs were accepted. Fix anything red before you move on. See [Debugging with request IDs](/debugging).

### Get the real restaurant ready

The real restaurant is a separate restaurant with its own slug. It is not the sandbox switched on: a sandbox is never live.

1. The owner of your partner account signs the partner agreement and the data processing agreement in the partner portal, under **Get started** (*Kom i gang*). Until they are signed, you cannot add real restaurants. A partner account that registered itself must also be approved by LettBestilt first.
2. Add the restaurant in the partner portal, or with `POST /api/v1/partner/restaurants` and a live partner key once LettBestilt Partner is open.
3. Invite the restaurant's owner with **Invite the owner** (*Inviter eieren*) on the restaurant in the partner portal (or `POST …/owner-invite` once live partner keys are available). The owner creates their own login, signs the customer agreement and the data processing agreement, and sets up online payment with SagaPay (with BankID). Partners cannot do these steps for the owner. The invitation is valid for 7 days, and you can send it again.
4. Add and verify every hostname the site runs on, on the restaurant's **Domains** tab (*Domener*), both `example.no` and `www.example.no` if you use both. You add a TXT record at the DNS provider and verify it yourself. See [Authentication](/authentication#trusted-browser-origin).
5. Set up the menu, opening hours and delivery like for any restaurant. The menu import reads a PDF or photo of the menu; see [Partner API](/partner-api#menu-import).

Until the restaurant is live, `/api/v1` answers `404 RESTAURANT_NOT_FOUND` for it (except `GET /site-gate`).

### Create the live key and webhooks

In the restaurant's API section in the partner portal, create a key. It is a live key (`lbs_live_…`). Give it only the scopes the site needs, or full access if you also want to manage the restaurant through the partner API. Then create the webhooks for the real restaurant, with the same events as in the sandbox. Each restaurant has its own webhooks and signing secrets. Webhooks carry customer data, so they can only be added once the owner has signed the agreements (`403 PARTNER_DATA_LOCKED` before that).

### Ask LettBestilt for go-live approval

The owner signs the agreements. LettBestilt approves the restaurant before the owner sets it live.

When the steps under **Get started** are done, choose **Ask for go-live approval** (*Be om go-live-godkjenning*) on the restaurant in the partner portal (or `POST …/go-live-review` once live partner keys are available). LettBestilt's checklist runs first and shows what must be fixed: menu, opening hours, payment, agreements, company details, website, domain, API key, owner, allergens and more. Then LettBestilt reviews the restaurant and you get an email with the decision. If it is rejected, the comment says why; fix it and ask again. An approval is valid for 30 days.

### Switch the site and go live

When LettBestilt has approved the restaurant, the owner sets it live under **Get started**. An approval never sets the restaurant live by itself.

Then change the environment variables in production and deploy:

```bash title="Production environment"
LETTBESTILT_SLUG=pizzaroma
LETTBESTILT_API_KEY=lbs_live_...
LETTBESTILT_WEBHOOK_SECRET=whsec_...
```

Keep the sandbox for testing future changes. A test key never works against a live restaurant, and a live key never works against a sandbox, so the two cannot be mixed up.

Work through the [go-live checklist](/go-live), then place one real order end to end with the restaurant.

</Steps>
