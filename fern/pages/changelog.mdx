Newest first. New fields, endpoints, error codes and events can appear in `/api/v1` at any time, so ignore what you do not recognise.

## 2026-10-19: Domains, owner invitations, go-live approval, menu import and MCP

**Only additive changes in `/api/v1`.** No endpoint, field or event was removed or renamed.

### New

- **[Domains](/partner-api#domains)** in the partner API: add a domain, get the TXT record, verify it yourself and choose the domain for tracking links. The same is on the restaurant's **Domains** tab in the partner portal. LettBestilt no longer has to verify domains for you.
- **[Owner invitations](/partner-api#inviting-the-owner)**: `POST` and `DELETE …/owner-invite` invite a real restaurant's owner by email. The owner creates their own login, signs the agreements and sets the restaurant live.
- **[Go-live approval](/partner-api#go-live-approval)**: a real restaurant needs LettBestilt's approval before it goes live for the first time. The owner signs the agreements. LettBestilt approves the restaurant before the owner sets it live. Ask for it in the partner portal, or with `POST …/go-live-review`. `GET /partner/restaurants/{slug}` has new `owner` and `goLive` objects.
- **[Menu import](/partner-api#menu-import)**: upload a menu as a PDF or photo, check the proposal and import it as a new menu that is turned off.
- **[MCP server](/mcp)** at `https://www.lettbestilt.no/api/mcp` for AI assistants such as Claude Code and Cursor. With the partner key, an assistant can read a restaurant's setup, create webhooks and domains, ask for go-live approval and place test orders in a sandbox. It cannot touch orders on real restaurants, customer data or keys, and it cannot delete anything. Until live partner keys are available, it works with a test partner key against sandboxes.
- **Partner team roles.** Test partner keys can be created by the owner, administrators and developers on your partner team; live partner keys only by the owner and administrators.

### Changed

- Owner invitations and go-live requests are for real restaurants, so through the API they need a live partner key. Live partner keys are still not available; until then, use the partner portal.
- A partner account that registered itself gets `403 PARTNER_NOT_APPROVED` from the partner API until LettBestilt has approved it.
- Webhooks for a real restaurant can only be added once its owner has signed the customer agreement and the data processing agreement (`403 PARTNER_DATA_LOCKED`).
- New error codes: `PARTNER_NOT_APPROVED`, `PARTNER_DATA_LOCKED`, `SANDBOX_NOT_SUPPORTED`, `DOMAIN_NOT_FOUND`, `DOMAIN_TAKEN`, `DOMAIN_LIMIT`, `DOMAIN_MANAGED`, `DOMAIN_NOT_VERIFIED`, `OWNER_EXISTS`, `OWNER_EMAIL_NOT_ALLOWED`, `OWNER_INVITE_NOT_FOUND`, `INVITE_SEND_FAILED`, the `GO_LIVE_…` codes, the menu import codes (`PDF_…`, `IMAGE_…`, `FILE_UNSUPPORTED` and `MENU_IMPORT_…`), and `NO_TABLE` and `INVALID_PARTY_SIZE`, which are reserved. The error code list in the API reference is now complete, including the reservation codes. See [Errors](/errors).

## 2026-10-16: Campaign tracking

### New

- **[Campaign tracking](/campaign-tracking).** A script for the restaurant's website, `https://www.lettbestilt.no/sporing/v1.js`, remembers the newsletter campaign a subscriber clicked for 30 days and hands it to the order with `LettBestilt.orderFields()`. Only newsletter subscribers are tracked, and the script sends nothing itself.
- `attributedCampaignId` in the `ORDER_CREATED` and `ORDER_PAID` webhooks: the campaign the order was credited to, or `null`.

## 2026-10-16: Partner API, scopes and sandbox payments

**Only additive changes in `/api/v1`.** No endpoint, field or event was removed or renamed. Existing keys keep full access, so integrations that work today keep working without changes.

### New

- **[Partner API](/partner-api)** under `/api/v1/partner`: list and create restaurants, read a restaurant's setup, delete a sandbox or archive a real restaurant, rotate and revoke restaurant keys, and create, list and delete webhooks. Server to server only.
- **Partner key** (`lbp_test_…`), created in the partner portal under **Settings → Partner key**. It only works against `/api/v1/partner`, together with the restaurant's own key in `X-LettBestilt-Restaurant-Key` for calls about one restaurant. Only test partner keys are available for now; they see and create sandboxes.
- **[Scopes](/authentication#scopes)** on restaurant keys. A key can be limited to some endpoints; a call outside them returns `403 INSUFFICIENT_SCOPE` with `error.details.requiredScope`. Existing keys keep full access.
- **[Expiry dates](/authentication#expiry-dates)** on keys, from tomorrow up to two years ahead. An expired key returns `401 KEY_EXPIRED`. The partner portal warns 14 days before.
- **[Sandbox payments](/payments#testing-payments-in-a-sandbox).** In a sandbox, `stripeUrl` points to a LettBestilt test page where the payment is approved or cancelled. `ORDER_PAID` is sent as usual, and no money moves.
- **[Webhook delivery log](/webhooks#delivery-log)** in the partner portal, with **Resend** (same `X-LettBestilt-Delivery-Id`, so receivers deduplicate), pause and resume, and changing events. Deliveries are kept for 30 days.
- **[`PING` test event](/webhooks#test-event)**, sent from the partner portal and signed like every other event. You cannot subscribe to it, and it is only sent when you ask for it.
- **[API log](/debugging#the-api-log)** per restaurant in the partner portal: status, route, key and request ID of each call, kept for 14 days, searchable by request ID, including an `X-Request-Id` you send yourself. **Check integration** sums up keys, domains, webhooks, errors and return URLs for the last 24 hours.

### Changed

- Restaurant endpoints in `/api/v1` accept only restaurant keys. A partner key there is rejected with `401 UNAUTHORIZED`.
- New error codes: `KEY_EXPIRED`, `INSUFFICIENT_SCOPE`, and the partner API's `IDEMPOTENCY_KEY_REQUIRED`, `PARTNER_AGREEMENT_REQUIRED`, `SLUG_TAKEN`, `SANDBOX_LIMIT`, `RETENTION`, `RESTAURANT_ARCHIVED`, `KEY_NOT_FOUND`, `KEY_IN_USE`, `WEBHOOK_NOT_FOUND`, `WEBHOOK_LIMIT` and `CHANGED`. See [Errors](/errors).
- In a sandbox, `successUrl` and `cancelUrl` on `POST /orders` can be left out; the customer then returns to the test page.
