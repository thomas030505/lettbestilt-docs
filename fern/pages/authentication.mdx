title: Authentication
subtitle: API keys for servers, verified domains for browsers
---

Every endpoint except order tracking needs one of two kinds of authentication: an API key, or a request from a trusted browser origin.

## API key (server to server)

Send the restaurant's API key as a bearer token:

```http
Authorization: Bearer lbs_...
```

- Keys are created **per restaurant** in the partner portal: **Restaurants → the restaurant → API keys and webhooks**. A key only works for that restaurant.
- Keys carry their environment: `lbs_test_…` for your sandbox restaurant, `lbs_live_…` for live restaurants. A test key never works against a live restaurant, and the other way round. Older keys that start with just `lbs_` keep working.
- The full key is shown only once. LettBestilt stores only a hash and cannot show it again.
- A restaurant can have several active keys. To rotate without downtime, choose **Rotate**: you get a new key, and the old one keeps working for up to 24 hours while you deploy it. **Revoke now** stops a key immediately, for example if it has leaked.
- If a request has an `Authorization` header, the key is always checked. A wrong key fails with `401`, even from a trusted origin.

<Warning>
Use the key only from your server. Never put it in browser code, a mobile app or a public repository.
</Warning>

## Trusted browser origin

When your site calls the API directly from the browser, for example to validate a coupon as the customer types, the request is authenticated by its `Origin` header instead of a key. Browsers set `Origin` themselves; there is nothing to configure in your code.

An origin is trusted for a restaurant when it is:

- the restaurant's LettBestilt subdomain, `https://{slug}.lettbestilt.no`
- one of the restaurant's **verified domains**, for example `https://www.pizzaroma.no`

Ask LettBestilt to verify every hostname your site runs on. `pizzaroma.no` and `www.pizzaroma.no` are two different origins, so verify both if you use both. Only `https` origins are accepted.

A verified domain also:

- allows the domain through CORS (`Content-Type`, `Authorization` and `Idempotency-Key` are allowed request headers)
- allows it as `successUrl` and `cancelUrl` when you create orders

## Which endpoints need what

| Endpoint | Authentication |
|---|---|
| `GET /orders/{token}` | None. The token is the secret |
| `GET /site-gate` | API key only. Browser origins are rejected |
| Everything else | API key **or** trusted browser origin |

## When authentication fails

The response is `401 UNAUTHORIZED`. `error.message` tells you why: a missing key, a wrong key, or an origin that is not trusted for this slug. See [Errors](/errors) for the envelope.
