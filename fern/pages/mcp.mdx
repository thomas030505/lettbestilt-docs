LettBestilt MCP is LettBestilt's MCP server, at `https://www.lettbestilt.no/api/mcp`. An AI coding tool that speaks the [Model Context Protocol](https://modelcontextprotocol.io) can use it to set up a restaurant and connect its website to LettBestilt while it writes the site: create a sandbox, set opening hours, delivery zones and settings, create and publish the menu, register the website's domains, set up webhooks, send test events, read the menu and the API log, place test orders in a sandbox, check the integration and ask LettBestilt for go-live approval. It also sets up your own partner account: your brand, contact and invoice details, sender domain and news to your restaurants.

The only thing a person does is create the keys in LettBestilt Partner (the partner portal) and put them in environment variables in the website's project. The AI tool does the rest.

<Note>
LettBestilt MCP sets things up; it never runs the restaurant. No tool deletes a menu, category, product, addon group, size, addon, delivery zone, override, webhook, domain, key or restaurant (`update_product` and `set_addon_group` reject a set that leaves out an existing size or addon; a person removes those in the dashboard or through the partner API), and no tool creates or rotates keys, invites owners, signs agreements, sets a restaurant live, touches payment, creates, changes, cancels or refunds orders in a real restaurant, or returns customer data. It never removes your logos (a new one replaces it) or your sender domain, never deletes or archives news, and never publishes news to real restaurants. Test orders only exist in sandboxes. Opening hours overrides are ended with a new `endDate` (the last day the override still applies), and delivery zones, menus, categories and products are turned off with `isActive: false`, never deleted.
</Note>

## Keys

The server uses the same two keys as the [LettBestilt Partner API](/partner-api):

| Header | Key | Needed for |
|---|---|---|
| `Authorization: Bearer …` | Your **partner key** (`lbp_test_…`, or `lbp_live_…` once LettBestilt Partner is open) | Every call |
| `X-LettBestilt-Restaurant-Key` | The restaurant's **restaurant key** (`lbs_test_…` or `lbs_live_…`) with access **Alt** (all) | Tools about one restaurant |

The partner key decides the environment. A test key reaches your sandboxes; a live key reaches your real restaurants. The two can never be mixed: a test partner key with a live restaurant key (or the other way round) is rejected.

<Note>
Live partner keys work once LettBestilt Partner is open. Until then, a live partner key gets `403 PARTNER_LIVE_KEYS_DISABLED` and LettBestilt MCP only works with sandboxes. When it is open, a live key also requires that LettBestilt has approved your partner account (`403 PARTNER_NOT_APPROVED`) and that you have signed the partner agreements (`403 PARTNER_AGREEMENT_REQUIRED`).
</Note>

The partner key alone is enough for `help`, `list_restaurants`, `get_tracking_setup`, `search_docs`, `create_sandbox`, `get_partner`, `get_partner_brand`, `get_partner_profile`, `get_sender_domain`, `list_partner_news`, `set_partner_brand`, `update_partner_profile`, `set_sender_domain`, `check_sender_domain`, `create_partner_news`, `update_partner_news` and `publish_partner_news`. Every other tool works on one restaurant, and the restaurant key decides which: one MCP connection reaches the one restaurant whose key is in `X-LettBestilt-Restaurant-Key`. Leave `slug` out and the tool uses that restaurant. `list_restaurants` shows all your restaurants in the environment, but a slug from that list only works when the restaurant key belongs to that restaurant; to work on another restaurant, put its restaurant key in the variable and restart the AI tool.

The website's limited restaurant key (for example menu and orders only) does not work here. Create a separate key with access **Alt** on the restaurant's **API** tab for the AI tool, and keep it in its own variable, `LETTBESTILT_MCP_RESTAURANT_KEY`. The website's own key usually lives in `LETTBESTILT_API_KEY`; using the same name for both either gives `INSUFFICIENT_SCOPE` or puts the AI tool's key with access **Alt** in the website's production environment.

### What the partner key alone can do

With only the partner key, LettBestilt MCP reads your partner account and the restaurants in the key's environment, searches the guides, creates sandboxes (test key only) and sets up your own partner account: your brand, contact and invoice details, sender domain and news (see [Your partner account](#your-partner-account)). Reading needs no role. Changes to your own account need a partner key **created by an owner or administrator** on your partner team: a key created by a developer, support or read-only member gets `403 KEY_ROLE_FORBIDDEN`, and the tool says so. Everything about one restaurant needs its restaurant key as well.

## Set up Claude Code

Put the keys in your shell, never in a file you commit:

```bash
export LETTBESTILT_PARTNER_KEY="lbp_test_..."          # lbp_live_... for a real restaurant, once LettBestilt Partner is open
export LETTBESTILT_MCP_RESTAURANT_KEY="lbs_test_..."   # the restaurant key with access Alt, only for the AI tool
```

Add `.mcp.json` to the root of your project. It only references the variables, so it is safe to commit:

```json .mcp.json
{
  "mcpServers": {
    "lettbestilt": {
      "type": "http",
      "url": "https://www.lettbestilt.no/api/mcp",
      "headers": {
        "Authorization": "Bearer ${LETTBESTILT_PARTNER_KEY}",
        "X-LettBestilt-Restaurant-Key": "${LETTBESTILT_MCP_RESTAURANT_KEY:-}"
      }
    }
  }
}
```

`${LETTBESTILT_MCP_RESTAURANT_KEY:-}` makes the restaurant key optional: without the `:-`, Claude Code refuses to start the server when the variable is not set. Start Claude Code in the project and run `/mcp` to check that `lettbestilt` is connected.

We recommend `.mcp.json` over `claude mcp add --header …`, which stores the key itself in your Claude Code settings.

## Set up Cursor

Add `.cursor/mcp.json` to the project. Cursor reads environment variables with `${env:…}`:

```json .cursor/mcp.json
{
  "mcpServers": {
    "lettbestilt": {
      "url": "https://www.lettbestilt.no/api/mcp",
      "headers": {
        "Authorization": "Bearer ${env:LETTBESTILT_PARTNER_KEY}",
        "X-LettBestilt-Restaurant-Key": "${env:LETTBESTILT_MCP_RESTAURANT_KEY}"
      }
    }
  }
}
```

Cursor does not read your shell's startup files when you open it from the Dock or Finder on macOS, so the variables are empty there. Start Cursor from the terminal where the variables are set (`cursor .`), or set them system-wide.

Both configurations are also on **Innstillinger → Partnernøkkel (API)** in the partner portal, ready to copy.

## Getting started and help

When you greet the AI tool, ask what it can do, or write "hjelp" or "help", it calls `help` and shows the LettBestilt MCP welcome card: what it can do, a few things to try (for example "Set opening hours 11–22 Monday to Saturday" or "Build the menu from my PDF and publish it"), the tools in six groups (Read, Connect, Operations, Menu, Sandbox and Your partner) and how to get more help. The server's instructions tell the AI tool to do this, and not before a concrete task: a session that starts with a task goes straight to it, without the card.

| You write | You get |
| --- | --- |
| "hjelp" or "help" | Every tool, one line each, by group |
| "hjelp meny" or "help menu" | One area: its tools and a short guide. The areas are `meny`/`menu`, `tider`/`hours`, `levering`/`delivery`, `innstillinger`/`settings`, `oppkobling`/`connect`, `sandkasse`/`sandbox`, `go-live` and `partner` (your own account) |
| "hjelp publish_menu" | One tool: what it does, whether it changes something and needs the restaurant key, every field with its type and format (from the tool's own schema), an example call and what it never does |

The card is in Norwegian by default. The AI tool passes `language: "en"` when you write English. `help` only needs the partner key, never calls anything outside the server and changes nothing.

In Claude Code the server also has two prompts: `/mcp__lettbestilt__welcome` shows the welcome card, and `/mcp__lettbestilt__help` shows the full overview, or help for the area or tool you give it (for example `/mcp__lettbestilt__help meny`). `/mcp__lettbestilt__help` takes an optional `language` argument, `nb` (the default) or `en`; `/mcp__lettbestilt__welcome` takes no arguments and always shows the Norwegian card.

The same card is shown on **Innstillinger → Partnernøkkel (API)** in the partner portal, under **Slik møter KI-verktøyet deg**.

## Tools

The 52 tools come in six classes. The class is fixed in the server and enforced on every call.

| Class | Tools | Restaurant | Changes something | Where | Extra limit |
|---|---|---|---|---|---|
| Read | 18 | Some | No | Sandboxes and real restaurants | |
| Setup | 10 | Yes | Some | Sandboxes and real restaurants | 60 per hour per partner key for the tools that change something |
| Configuration | 14 | Yes | Yes | Sandboxes and real restaurants | 300 per hour per partner key |
| Partner | 1 | No | Yes | Test partner key only | The partner API's limits for creating restaurants |
| Partner account | 7 | No | Yes | Test and live partner keys | 60 per hour per partner key |
| Sandbox only | 2 | Yes | Yes | Sandboxes only | 30 test orders per hour per partner key |

Tools that only read are marked `readOnlyHint`. `publish_menu`, `set_menu_schedule`, `update_category`, `update_product` and `set_addon_group` are also marked `destructiveHint`: they delete nothing, but they can take something customers see out of service or change prices and the sets of sizes and addons customers order, so an AI tool that respects the hint asks you before it runs them. `set_partner_brand`, `set_sender_domain` and `publish_partner_news` are marked `destructiveHint` too, because your restaurant owners see the result.

**Setup** (sandboxes and real restaurants):

| Tool | What it does |
|---|---|
| `list_webhooks` | The restaurant's webhooks, never the secret |
| `create_webhook` | Registers a public `https://` URL for the chosen events. The signing secret is in the response **once**; store it as an environment variable on the receiving server. On a real restaurant the webhook is only active when the URL's host is a domain of the restaurant that a person verified (or a subdomain of one), or your website; otherwise it is created paused (`paused: true`). A domain verified with `verify_domain` does not count |
| `set_webhook_active` | Pauses or resumes a webhook (pass `expectedActive` to fail with `CHANGED` instead of overwriting someone else's change). It cannot resume a webhook on a real restaurant whose host is not trusted (`WEBHOOK_HOST_NOT_TRUSTED`); a person does that in the partner portal |
| `send_test_webhook` | Sends a signed `PING` (no customer data) to a webhook that is already registered |
| `list_domains` | The restaurant's domains, verified or not, with the TXT record a domain still waits for |
| `add_domain` | Adds the website's host and returns the TXT record to create |
| `verify_domain` | Looks up the TXT record and verifies the domain |
| `set_primary_domain` | Chooses the verified domain order tracking links go to |
| `get_go_live_status` | For a real restaurant: whether it needs approval, where the request stands and what is missing |
| `request_go_live` | Asks LettBestilt to review a real restaurant before it goes live. An approval never sets it live: the owner does that |

**Configuration** (sandboxes and real restaurants; changes the restaurant's own setup, never deletes):

| Tool | What it does |
|---|---|
| `set_opening_hours` | Replaces the whole week (`PUT …/hours`). A weekday you leave out is closed. The same week twice changes nothing |
| `add_hours_override` | Adds an exception for a date range: a public holiday, a holiday or summer hours (`POST …/hours/overrides`) |
| `update_hours_override` | Changes an override. `endDate` is inclusive: today's date keeps the override for the rest of today. To lift an override that covers today, set `isClosed: false` with the normal hours (`opensAt`/`closesAt`), or shorten `endDate` to yesterday only for overrides that started before today. Send `expectedUpdatedAt` from `get_opening_hours` |
| `create_delivery_zone` | A zone by postal codes or by radius, with fee, minimum order and estimated minutes in øre and minutes (`POST …/delivery-zones`) |
| `update_delivery_zone` | Changes a zone, or turns it off with `isActive: false`. Turning off the last active zone stops delivery while `deliveryEnabled` is still on |
| `update_settings` | Changes the settings you send (`PATCH …/settings`); send `expectedVersion` from `get_settings`. On a real restaurant that is live, `website` and `googleReviewUrl` give `403 HUMAN_REQUIRED`: a person changes them. The legal fields (organisation number, legal name, legal address) are only changed when the person asked for exactly that, and are locked once the owner has signed (`LEGAL_LOCKED`). Free text (name, description, cuisine, tracking and receipt texts) is cleaned like menu text, with `textCleaned` in the response when something was removed |
| `create_menu` | Creates a **new** menu from a proposal the AI tool builds from the menu the person gave it (`POST …/menus`). The new menu is always off and not the default, so customers see nothing yet and no other menu is touched. Not idempotent: check `list_menus` first |
| `publish_menu` | The only tool that puts a menu in service or takes it out (`PATCH …/menus/{menuId}`): `isActive`, `isDefault`, `startsOn`, `endsOn`. See [Publish a menu](#publish-a-menu) |
| `set_menu_schedule` | Replaces the menu's whole time schedule (`PUT …/menus/{menuId}/schedules`): weekday, `startsAt` and `endsAt` (`HH:MM`, Oslo). An empty list removes it |
| `add_category` | Adds a category to a menu (`POST …/menus/{menuId}/categories`) and returns its id for `add_products` |
| `update_category` | Changes a category (`PATCH …/categories/{categoryId}`), or hides it and its products with `isActive: false` |
| `add_products` | Adds 1 to 50 products in one call (`POST …/products/batch`), all or nothing: one invalid product fails the call with the path in `details.issues` (for example `products.2.categoryId`) and nothing is saved |
| `update_product` | Changes a product (`PATCH …/products/{productId}`): price, description, allergens, sizes, `isAvailable` (sold out for now), `isActive` (hidden for good). Sizes are sent as the whole set with their `id`; a set that leaves out an existing size gives `VALIDATION_FAILED`. Always sends `expectedVersion`, the product's `version` from `get_menu`; `CHANGED` means the product changed after it was read |
| `set_addon_group` | Without `groupId`: creates an addon group (`POST …/addon-groups`). With `groupId`: changes it (`PATCH …/addon-groups/{groupId}`) with `expectedVersion` from `get_menu`; addons are sent as the whole set with their `id`, and a set that leaves out an existing addon gives `VALIDATION_FAILED`. `minSelect` can be at most the number of available addons, and `isRequired` must agree with `minSelect` (true exactly when it is above 0); a required `GLOBAL` group comes back with a warning, since every product then needs a choice |

These tools call the [partner API endpoints for setting up a restaurant](/partner-setup-api) in the same process, with both keys. They validate, rate limit and fail exactly like the API: a format error comes back as `VALIDATION_FAILED` with the field in `details.issues`, and `CHANGED`, `LEGAL_LOCKED`, `DEMO_RESTAURANT`, `MENU_NOT_FOUND`, `CATEGORY_LIMIT` and the other codes come back unchanged. `RATE_LIMITED` carries `details.retryAfterSeconds`.

**Partner** (no restaurant; test partner key only):

| Tool | What it does |
|---|---|
| `create_sandbox` | Creates a sandbox from `name` (and optionally `slug`, `pickupEnabled`, `deliveryEnabled`). Without `slug`, one is made from the name. It **never returns a restaurant key**: the response says to create one with access **Alt** on the sandbox's **API** tab in LettBestilt Partner, put it in `LETTBESTILT_MCP_RESTAURANT_KEY` and restart the AI tool |

With a live partner key it gives `403 SANDBOX_TEST_KEY_REQUIRED`: real restaurants are created by a person in LettBestilt Partner or with the partner API. A partner can have up to 20 sandboxes (`409 SANDBOX_LIMIT`); a sandbox is deleted with `DELETE /api/v1/partner/restaurants/{slug}`, never through MCP. A retry after a timeout creates a new sandbox, so check `list_restaurants` first.

**Partner account** (no restaurant; test and live partner keys; your own account, never a restaurant's):

<Warning>
Your brand, profile and sender domain belong to you as a partner, not to an environment. A test key changes what real restaurant owners see, also while LettBestilt Partner is closed. Only news is bound to the key's environment.
</Warning>

| Tool | What it does |
|---|---|
| `set_partner_brand` | Changes `supportEmail`, `supportPhone`, `showPoweredBy` and, with white label, the owners' dashboard colours and font (`themeSidebarColor` and `themeActionColor` as hex with a contrast of at least 4.5:1, `themeFont` from the list; `null` restores the default) (`PATCH /api/v1/partner/brand`). A new logo replaces the previous one, and the previous file is deleted only when LettBestilt has a record that you uploaded it. The logos cannot be removed or set to a link through MCP. Two large logos may not fit in one request; send them in two calls. Send `expectedUpdatedAt` from `get_partner_brand`. It never changes your website: a person sets that in LettBestilt Partner or with the partner API, because it decides which webhook hosts are trusted |
| `update_partner_profile` | Changes the contact and invoice details you send (`PATCH /api/v1/partner/profile`); send `expectedUpdatedAt` from `get_partner_profile`. The legal name and organisation number never change here |
| `set_sender_domain` | Registers your sender domain (white label only) and returns the DNS records (`POST /api/v1/partner/brand/sender-domain`). A person adds them at the DNS provider; the AI tool never changes DNS |
| `check_sender_domain` | Checks the DNS records again (`POST …/sender-domain/verify`) and says whether the domain is verified |
| `create_partner_news` | Creates a news draft to your restaurants (`POST /api/v1/partner/news`). With a test key, news goes to sandboxes you name in `restaurantSlugs`; with a live key, to real restaurants |
| `update_partner_news` | Changes a draft (`PATCH /api/v1/partner/news/{newsId}`), with `expectedUpdatedAt` |
| `publish_partner_news` | `publish`, `schedule` (with `scheduledAt`) or `unschedule` a news item (`POST …/news/{newsId}/publish`). With a test key it publishes to sandboxes. With a live key, `publish` and `schedule` give `403 HUMAN_REQUIRED`: the AI tool writes drafts for real restaurants, and a person publishes them in LettBestilt Partner or with the partner API. These tools call [the partner API endpoints for your own account](/partner-setup-api#your-own-partner-account) in the same process, with only the partner key, so they validate, rate limit and fail like the API: `KEY_ROLE_FORBIDDEN` (the key was not created by an owner or administrator), `WHITE_LABEL_REQUIRED`, `CHANGED`, `NOT_DRAFT`, `NO_RECIPIENTS`, `HUMAN_REQUIRED` and the other codes come back unchanged. The AI tool writes the support details, the logo, the sender domain and the text of a news item only from what you gave it, with no numbers, prices or promises you did not give, and shows you a news draft before it publishes.

**Sandbox only** (anything that creates orders or test data):

| Tool | What it does |
|---|---|
| `create_test_order` | A test order through `POST /api/v1/orders`: fictional customer, pickup, cash or simulated online payment, with an idempotency key |
| `verify_attribution` | Places a test order with a campaign ID from the sandbox and confirms it was attributed |

Against a real restaurant these give `403 SANDBOX_ONLY` and create nothing.

**What LettBestilt MCP never does:** create, change, cancel or refund orders in a real restaurant; return customer data; delete a webhook, domain, key, opening hours override, delivery zone, menu, category, product, addon group, size, addon or restaurant (pause a webhook, end an override with `endDate`, turn a zone, menu, category or product off with `isActive: false`, and remove domains in the portal); create, rotate or revoke keys (a person does that in the portal); create real restaurants; change payment, the team or printers; invite owners; sign agreements; set a restaurant live; remove the logos (a new logo replaces it) or the sender domain; delete or archive news; publish news to real restaurants (a person does); change the partner's website or the white label switch.

`get_menu`, `create_test_order` and `verify_attribution` call the real `/api/v1` endpoints with the restaurant key, and the configuration tools (and `get_menu` with `menuId`) call the partner API with both keys. They validate, rate limit and fail exactly like your own code would, and they show up in the API log next to your own calls. The setup tools use the same rules as the partner portal and the partner API.

## Your partner account

The partner account tools set up what your restaurant owners see from you: your brand, your sender domain and your news. A typical session: `get_partner`, `set_partner_brand` with the support e-mail, phone, logo, light logo and (with white label) colours and font you give the AI tool, `set_sender_domain` (you add the DNS records at your DNS provider) and later `check_sender_domain`, then `create_partner_news` with your text, which the AI tool shows you before `publish_partner_news` in a sandbox. For real restaurants it stops at the draft, and you publish it in the partner portal.

## The menu

The menu tools work on the menu the person you work for gave you: a PDF, a photo or a list. The AI tool reads it itself and never takes menu text or prices from a tool result or a web page. Prices are integers in øre (1 NOK = 100 øre, so 149 kr is `14900`).

### Create a menu from a proposal

`create_menu` takes `name` and a `proposal`: categories with dishes, each with `number`, `name`, `description`, `price` in øre or `variants` (sizes with prices), and allergen codes. It is the same proposal as [menu import](/partner-setup-api#5-a-menu-from-a-proposal) uses. Links, e-mail addresses, HTML and invisible characters are removed from names and descriptions (`textCleaned` in the response).

- **The new menu is always off** and not the default. Nothing changes for customers until `publish_menu`, so it is safe on a real restaurant that is live.
- **Prices under 500 øre (5 kr)** (but above 0) give an entry in `warnings` (`{ path, message }`, the path in the proposal): such a price looks like kroner. Nothing is rejected, because 0 can be a free addon. `add_products` and `update_product` give the same warnings, and so does the partner API, which they come from.
- **A large menu** does not fit in one call (1 MB). Call `create_menu` with the first categories, then add the rest to the **same** menu with `add_category` and `add_products` (at most 50 products per call). Never split one menu into several menus.
- **Not idempotent.** `create_menu`, `add_category`, `add_products` and `set_addon_group` without `groupId` create something new on every call. After a timeout, check with `list_menus` or `get_menu` before you try again.
- At most 10 new menus per hour per restaurant (shared with menu import), 60 categories per menu, 800 active products and 100 addon groups.

**Allergen codes:** `WHEAT`, `RYE`, `BARLEY`, `OATS`, `SPELT`, `KAMUT`, `CRUSTACEANS`, `EGGS`, `FISH`, `PEANUTS`, `SOYBEANS`, `MILK`, `NUTS`, `CELERY`, `MUSTARD`, `SESAME`, `SULPHITES`, `LUPIN` and `MOLLUSCS`. Only the allergens the menu states, never a guess. A menu that numbers the 14 EU allergens is read as 1 = `WHEAT`, 2 = `CRUSTACEANS`, 3 = `EGGS`, 4 = `FISH`, 5 = `PEANUTS`, 6 = `SOYBEANS`, 7 = `MILK`, 8 = `NUTS`, 9 = `CELERY`, 10 = `MUSTARD`, 11 = `SESAME`, 12 = `SULPHITES`, 13 = `LUPIN` and 14 = `MOLLUSCS`, unless the menu has its own legend. Gluten without a named grain becomes `WHEAT`, and the AI tool asks the person to check which grain.

### Read a menu with `get_menu`

`get_menu` with `menuId` (from `list_menus` or `create_menu`) reads one menu through the partner API, also when it is off or the restaurant is not live yet. Use it to check a new menu against the menu the person gave you before you publish it.

The response is compact so a menu of a few hundred products fits: each product lists its `addonGroupIds`, and each addon group is listed once in `addonGroups`, with its addons and the `categoryIds` and `productIds` it applies to. Sizes carry `id`, `isDefault` and `addonTierKey`. Fields with their default value are left out, and `defaults` in the response says what they are (`isActive` and `isAvailable` true, `isDefault` false, `addonTierKey` null). A menu with more than 100 products comes back as an overview without descriptions and allergens (`compact: true`): read it one category at a time with `categoryId`.

Without `menuId`, `get_menu` reads the menu customers see now through `GET /api/v1/menu`, as your website does.

### Publish a menu

`publish_menu` is the only tool that puts a menu in service, in one of three ways:

- (a) To replace the main menu for a period (for example a Christmas menu instead of the normal one): publish_menu `{ isActive: true, startsOn, endsOn, priority }` without isDefault, with priority higher than the main menu's (read it in list_menus), then set_menu_schedule on it with all seven days 00:00–23:59; in the period only it is shown, and after endsOn the main menu is back by itself. Both are needed: without the schedule the menu is never shown, and when the main menu has a schedule of its own, equal priority shows both menus and a lower one shows only the main menu.
- (b) To show a menu next to the main menu in a period: publish_menu `{ isActive: true, isDefault: true, startsOn, endsOn }`; the main menu stays the default (defaultKept: true) and customers see both menus in the period.
- (c) A new main menu: publish_menu `{ isActive: true, isDefault: true }` without dates; it replaces the previous main menu (previousDefaultMenuIds).

A menu with dates but without isDefault or a schedule is never shown while another menu is the default.

Dates are `YYYY-MM-DD` in Norwegian time, and both are inclusive. `publish_menu { isActive: false }` takes a menu out of service; menus are never deleted. The response has `publication`, `defaultKept`, `warnings` (for example when no menu is visible any more) and `notice`. On a real restaurant that is live, the AI tool confirms with the person before `publish_menu`.

`set_menu_schedule` sets the windows a scheduled menu (for example lunch) is shown in. When the windows of two scheduled menus overlap, the menu with the higher `priority` is shown, and with equal priority customers see both. That is the menu's `priority` (set with `publish_menu`, shown in `list_menus`; reordering menus in the dashboard rewrites it, top is highest); `priority` on a schedule row is stored but not used.

Websites can show the old menu for a few minutes, because `GET /api/v1/menu` is cached.

### Change a menu that is in service

Only `create_menu` waits for `publish_menu`. `add_products`, `update_product`, `update_category` and `set_addon_group` on a menu that is in service, and any `GLOBAL` addon group, reach customers right away (after the cache). On a real restaurant that is live, the AI tool confirms with the person before `update_category { isActive: false }` and `set_addon_group`.

- **Sizes and addons keep their `id`.** `update_product` replaces the whole set of `variants`, and `set_addon_group` with `groupId` replaces the whole set of `addons` (and `productIds`). Read the menu with `get_menu` first and send every existing size or addon with its `id` (and `isDefault` and `addonTierKey` for sizes). One without `id` is created new. Leaving out an existing one gives `VALIDATION_FAILED` (path `variants` or `addons`): LettBestilt MCP never removes a size or an addon, a person does that in the dashboard or through the partner API. A new id breaks orders from baskets that still hold the old one, for up to six minutes. `add_products` and a new addon group take no `id` (`VALIDATION_FAILED`).
- **Nothing is deleted.** Hide a product for good with `isActive: false`, mark it sold out for now with `isAvailable: false`, and hide a category and its products with `update_category { isActive: false }`.
- **`CHANGED`** means someone changed the same category, product or group in between. Every product and addon group in `get_menu` has a `version`, and `update_product` and `set_addon_group` send it as `expectedVersion`, so a change the owner made after the AI tool read the menu is never overwritten. Read it again with `get_menu` and send the change once more.
- Images cannot be set from LettBestilt MCP; set them in the restaurant dashboard.

## Set up a restaurant from scratch

1. `create_sandbox` with the restaurant's name, if there is no sandbox yet. A person creates the restaurant key for it in LettBestilt Partner and restarts the AI tool with the key in `LETTBESTILT_MCP_RESTAURANT_KEY`. For a real restaurant, a person creates it in LettBestilt Partner instead, and the steps below are the same with a live key.
2. `get_settings`, then `update_settings` with the name, description, phone, visiting address, colours and ordering options the person gave you, and `expectedVersion` from `get_settings`.
3. `set_opening_hours` for the week, and `add_hours_override` for holidays.
4. `create_delivery_zone` for each area the restaurant delivers to, if it delivers.
5. `list_menus`, then `create_menu` from the menu the person gave you. For a large menu, `add_category` and `add_products` add the rest to the same menu.
6. `get_menu` with `menuId` to check names, prices, sizes and allergens against the menu. Fix mistakes with `update_product` and `update_category`.
7. `publish_menu` with `{ isActive: true, isDefault: true }`: the restaurant's main menu.
8. Domains and webhooks: `add_domain`, `verify_domain` and `set_primary_domain` for the website's hosts, then `create_webhook` and `send_test_webhook`. See [How the AI tool connects a website](#how-the-ai-tool-connects-a-website).
9. `create_test_order` in the sandbox to test the ordering flow end to end, and `check_integration` until it is green.
10. For a real restaurant: `get_go_live_status`, fix what is missing, then `request_go_live`. LettBestilt reviews it, and the owner sets the restaurant live.

## How the AI tool connects a website

A typical session, once the keys are in the environment:

1. `get_restaurant_setup` to see the restaurant the key belongs to and what is missing.
2. `add_domain` for each host the website uses (`restaurant.no` and `www.restaurant.no` are two domains). Create the TXT records at the DNS provider, then `verify_domain`, and `set_primary_domain` for the host tracking links should use. Verified domains are also what lets the website call `/api/v1` from the browser and use its own `successUrl` and `cancelUrl`. On a real restaurant, a domain the AI tool verified does not make a webhook to it active; see [Security](#security).
3. `create_webhook` with the website's receiving URL and events. Store the secret as an environment variable on that server and verify `X-LettBestilt-Webhook-Signature`. `send_test_webhook` and `list_webhook_deliveries` confirm that events arrive.
4. `get_menu`, build the ordering flow, and in a sandbox `create_test_order` to test it end to end. `get_api_log` explains failed calls.
5. `check_integration` until it is green.
6. For a real restaurant: `get_go_live_status`, fix what is missing, then `request_go_live`. LettBestilt reviews it, and the owner sets the restaurant live.

## Test orders

`create_test_order` uses the first product that needs no choices when you leave `items` out. `payment` is one of:

- `auto` (default): cash if the sandbox takes cash. Otherwise the order waits for a simulated online payment, and the tool returns `paymentUrl`, the test payment page where you pay or cancel.
- `cash`: a cash order.
- `online`: returns `paymentUrl`, the test payment page, where you can pay or cancel.
- `online_paid`: pays right away, so `ORDER_PAID` goes to your webhooks. If the test payment fails, the order still exists: the error `SANDBOX_PAYMENT_UNAVAILABLE` carries `orderId`, `idempotencyKey` and `paymentUrl` in `details`.

Send the same `idempotencyKey` again to retry without creating a second order; the response then has `replayed: true` and shows the order as it is. Without one, every call creates a new order, and the tool returns the key it made. A sandbox that is closed right now rejects the order like the API does; set opening hours in the sandbox first.

`verify_attribution` takes the same `items`. Pass them when every product in the sandbox needs a choice (a required addon group); otherwise the tool stops with `NO_ORDERABLE_PRODUCT` before it creates a draft campaign. Items that cannot be ordered give `ITEM_NOT_ORDERABLE`, also before the draft.

## Limits

- 120 calls per minute per partner key, shared with the partner API. Each message in a JSON-RPC batch counts as one call.
- Changes to webhooks, domains, opening hours, delivery zones, settings and the menu also share the partner's 30 per minute (per environment, so testing in sandboxes never slows a real restaurant) with the portal and the partner API.
- Setup tools that change something (webhooks, domains, test events, go-live requests): 60 per hour per partner key.
- Configuration tools that change something (opening hours, delivery zones, settings and the menu): 300 per hour per partner key. The two hourly limits are separate, so a large menu never blocks webhooks and domains, and the other way round.
- Partner account tools that change something: 60 per hour per partner key, separate from the other two, plus the partner API's own limits, shared with the portal: 10 sender domain changes per hour and 10 checks per 10 minutes, 10 logo uploads per hour (both logos together), 60 news changes per 10 minutes and 10 news sends per day per partner.
- `create_sandbox`: the partner API's limits for creating restaurants (10 per hour per partner key and 20 per hour per partner) and at most 20 sandboxes.
- Test orders and `verify_attribution`: 30 per hour per partner key.
- `create_menu`: 10 new menus per hour per restaurant, shared with menu import.
- `send_test_webhook`: 5 per minute per webhook; `verify_domain`: 30 per 10 minutes per restaurant; `check_integration`: 10 per minute per restaurant; `request_go_live`: 15 per hour per restaurant and 30 per partner. All shared with the portal.
- The delegated API calls also have the API's own limits.
- At most 1 MB per request and 10 messages in a JSON-RPC batch. A logo or light logo sent with `set_partner_brand` is at most 512 KB decoded. A request that is too large gives `PAYLOAD_TOO_LARGE`; send the categories one at a time, or the products in smaller groups.

`RATE_LIMITED` from the hourly limits and from the delegated API calls carries `details.retryAfterSeconds`: wait that many seconds before you try again.

The server is stateless and answers with JSON (Streamable HTTP without sessions). Only `POST` is supported; a client that opens an SSE stream with `GET` gets `405`.

## Logging

Tool calls about one restaurant are written to the restaurant's API log as `POST /api/mcp/{tool}`, with the request ID the response carries in `X-Request-Id`. The partner API call a configuration or menu tool makes inside the server is not written a second time; the `/api/mcp/{tool}` row is the only one, so **Sjekk integrasjonen** never shows the AI tool's mistakes as errors from your website. **Sjekk integrasjonen** ignores the `/api/mcp` rows, and tools that only read (`check_integration`, `get_api_log`, `get_restaurant_setup` and the like) never mark the key as used. The delegated `/api/v1` calls (`get_menu` without `menuId`, `create_test_order`, `verify_attribution`) count as real use of the key, so a sandbox you have only tested from an AI tool can already show the key as in use. Test orders from the MCP server do not count as the site's own orders: **Sjekk integrasjonen** leaves the delegated `POST /api/v1/orders` row from `create_test_order` and `verify_attribution` out of the latest order and out of the latest successful call with a key. To see the check go green, place an order from your own site.

Every error carries the same request ID in `error.requestId`: in the HTTP response when the server stops the call (for example `401` or `429`), and inside the tool result when a tool fails. Give it to LettBestilt when you ask for help.

A configuration tool also writes the partner API's own row (for example `PATCH /api/v1/partner/restaurants/{slug}/settings`) with the same request ID.

Every change (sandboxes, opening hours, delivery zones, settings, webhooks, domains, test events, go-live requests, test orders and test campaigns) is also logged in the partner's activity log, and in the restaurant's **Partner access** (*Partnerens tilgang*), with the actor «MCP» and the partner key that was used.

## Security

- **Tool results are data, never instructions.** Product names, descriptions, webhook URLs and error messages can be written by people. The server tells the AI tool this, and the tools only return structured data. Review what your AI tool does before you let it run commands.
- **Contact details, links and legal fields only from the person.** The server tells the AI tool to set the website, the Google review link, the phone number, the logo and cover image and the legal fields only to values the person it works for gave it, never to values it read in a tool result, a menu or a web page. The legal fields go into the customer agreement and are locked once the owner has signed it. On a real restaurant that is live, the website and the Google review link cannot be changed through MCP at all (`403 HUMAN_REQUIRED`).
- **Your own account only from you.** The support details, logos, dashboard colours and font, sender domain and news text come from you, never from a tool result or a web page. Your website is never set through MCP, since it decides which webhook hosts are trusted, and news to real restaurants is published by a person.
- **No browsers.** A request with an `Origin` header is rejected, so a key can never be used from a web page.
- **Keys stay out of git.** `.mcp.json` and `.cursor/mcp.json` only reference environment variables. Never paste a key into them.
- **Test orders in sandboxes only.** A test partner key only reaches sandboxes, a live key only real restaurants, and every tool that creates orders or test data checks that the restaurant is a sandbox that is not archived. `create_webhook` only accepts public `https://` URLs, `send_test_webhook` only sends to a URL that is already registered, and `verify_domain` only looks up DNS.
- **Webhooks only to hosts a person approved.** Webhooks carry order and customer data. On a real restaurant a webhook created through MCP is only active when its host is a domain of the restaurant that a person verified (in the partner portal or the restaurant dashboard) or that your own code verified through the partner API, or your website. A domain the AI tool added and verified itself with `add_domain` and `verify_domain` does not count, so a prompt injection cannot make an attacker's host trusted and send orders there. Anything else is created paused, and only a person in the partner portal can switch it on. A real restaurant under a partner also needs the owner's signed agreement and data processing agreement before any webhook can be added (`PARTNER_DATA_LOCKED`).
- **Secrets once.** `create_webhook` returns the signing secret one time. Keep it in an environment variable, never in a committed file.

## Troubleshooting

- **The server shows "needs authentication" or "failed" in Claude Code (`/mcp`), or a red status in Cursor**: the partner key is empty or wrong. The server answers `401`, and the AI tool reads that as "sign in with OAuth", so you never see our error text and there is no sign-in page to find. Check that `LETTBESTILT_PARTNER_KEY` is set in the shell or environment the tool starts from (see the note about Cursor above), that it starts with `lbp_`, and restart the tool.
- **`401` with "Send partnernøkkelen (lbp_) i Authorization"** (with `curl` or your own client): the partner key did not reach the server.
- **`RESTAURANT_NOT_FOUND` for a restaurant `list_restaurants` just showed**: the restaurant key decides which restaurant the tools reach. One connection reaches only the restaurant its restaurant key belongs to. Leave out `slug` to use the key's restaurant, or set `LETTBESTILT_MCP_RESTAURANT_KEY` to a key for the restaurant you want and restart the AI tool.
- **`403 PARTNER_LIVE_KEYS_DISABLED`**: you used a live partner key before LettBestilt Partner is open. Use a test key against a sandbox.
- **`403 SANDBOX_ONLY`**: test orders and attribution checks only run in sandboxes.
- **`403 SANDBOX_TEST_KEY_REQUIRED`**: `create_sandbox` needs a test partner key.
- **`403 KEY_ROLE_FORBIDDEN`** from a partner account tool: the partner key was created by a developer, support or read-only member. Reading still works. An owner or administrator creates a partner key under **Innstillinger → Partnernøkkel (API)**. A rotated key counts as created by the person who rotated it, so a developer who rotates the owner's key gets `403 KEY_ROLE_FORBIDDEN` on brand, profile and news; LettBestilt Partner shows per key whether it can change the partner's own settings.
- **`403 HUMAN_REQUIRED`**: a person does this one: publishing news to real restaurants, setting your website, or changing `website` or `googleReviewUrl` on a real restaurant that is live. Do it in LettBestilt Partner or with the partner API.
- **`CHANGED` from a configuration tool**: someone changed the same thing in between. Read it again (`get_settings`, `get_opening_hours`, `list_delivery_zones`, `get_menu` with `menuId`) and send the change again, with the new `expectedVersion` or `expectedUpdatedAt` where the tool takes one.
- **A published menu does not show up**: a menu with dates but without `isDefault` or a schedule is never shown while another menu is the default; see [Publish a menu](#publish-a-menu). `list_menus` shows `isLiveNow`, and websites can show the old menu for a few minutes because of caching.
- **`INSUFFICIENT_SCOPE` from a tool**: the restaurant key does not have access **Alt**. Often it is the website's own limited key. Create a separate key with access **Alt** for the AI tool and put it in `LETTBESTILT_MCP_RESTAURANT_KEY`.
- **A webhook is created with `paused: true`**: its host is not a domain a person verified, or your website. Switch it on in the partner portal under the restaurant's **Webhooks** tab if the address is right.
